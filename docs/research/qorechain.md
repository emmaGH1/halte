## 6. QoreChain technology

**PUBLISHED** — QoreChain is a Layer 1 with an Ethereum-compatible EVM, QoreChain Native (CosmWasm), and a Solana-compatible SVM. EVM contracts use Solidity and normal Ethereum tooling. Native contracts use Rust/Wasm. SVM programs target BPF. The v3.2.8 upgrade initially closed Diana execution and testnet governance proposal 37 reopened it. Public SVM JSON-RPC remains read-only. Sending SVM transactions on Diana requires a self-hosted node. Mainnet execution remains off. Native contract upload is governed. Testnet users can instantiate approved stored code, while mainnet ordinary upload and instantiation remain paused. [Core repository](https://github.com/qorechain/qorechain-core) · [Chain developer kit](https://docs.qorechain.io/developer-tools/chain-dev-sdk/) · [Cross-VM guide](https://docs.qorechain.io/developer-guide/cross-vm-interoperability/) · [Version history](https://docs.qorechain.io/appendix/version-history/) · [SVM lane guide](https://docs.qorechain.io/developer-guide/svm-lane-v328/)

- **PUBLISHED** — Current consensus uses standard stake-weighted proposer rotation. Triple-Pool Composite Proof-of-Stake is implemented as a module, with the proposed pool-weighted mechanics unwired from live block production, rewards, slashing and governance tally. PRISM observes in mainnet conservative mode without policy weights and runs a demonstration policy in testnet shadow mode without applying parameter changes. **INFERRED (live check)** — Diana's PRISM REST route returned mode `shadow` and `applied: false`. [Consensus](https://docs.qorechain.io/architecture/consensus-mechanism/) · [PRISM](https://docs.qorechain.io/architecture/prism-consensus-engine/) · [Live PRISM result](https://api-testnet.qore.host/qorechain/rlconsensus/v1/last_action)
- **PUBLISHED** — Native transactions combine secp256k1 and ML-DSA-87. An ordinary EVM transaction retains Ethereum format and requires a registered ML-DSA-87 key and a separately opened hybrid-signed authorization window. Windows bound duration in blocks, transaction count and value plus fees, and optionally restrict recipients. Target-restricted windows refuse contract creation. QoreSeal uses ML-KEM-1024 with X25519 by default and supports an on-chain recipient key registry. For eth-native accounts `0x…` and `qor1…` encode the same account, with QOR displayed at 18 decimals on EVM and six on the native lane. [Chain developer kit](https://docs.qorechain.io/developer-tools/chain-dev-sdk/) · [QoreSeal](https://github.com/qorechain/qoreseal) · [Workshop 3](https://docs.qorechain.io/build-before-qday/workshop-3/)
- **PUBLISHED** — Official QoreX releases include Chrome, Firefox, macOS, Android and iOS. The browser wallet has native hybrid signing and supported message signing via `signArbitrary`. QoreX EVM account connection is supported in the viem/wagmi template and its EVM signing methods are documented as unavailable there. MetaMask or another injected EIP-1193 wallet can sign ordinary EVM transactions once the account's PQC key and window are set up through QoreX, Dashboard or SDK. Keplr, Leap and Cosmostation need the QoreChain wallet adapter for native hybrid sends. MetaMask and Phantom can also supply linked authenticator keys through adapter flows, distinct from sending transactions over the SVM lane. Fest registration specifically requires QoreX. [QoreX releases](https://www.qorechain.io/qorex) · [Wallet adapter](https://docs.qorechain.io/developer-tools/wallet-adapter/) · [Chain developer kit](https://docs.qorechain.io/developer-tools/chain-dev-sdk/) · [Signing FAQ](https://build.qorechain.io/faq#qorex) · [Registration](https://build.qorechain.io/register)

## 7. Hour-1 gate

1. **PUBLISHED** — Use a throwaway QoreX wallet on Testnet. For the EVM lane choose an Ethereum/coin-60 account and identify both `qor1…` and `0x…` forms. For a CLI-first deployment, Workshop 1 and chain developer kit show how to derive an eth-native test account in the scaffold, then check which address will spend before funding it. [Prerequisites](https://docs.qorechain.io/build-before-qday/prerequisites/) · [Workshop 1](https://docs.qorechain.io/build-before-qday/workshop-1/) · [Chain developer kit](https://docs.qorechain.io/developer-tools/chain-dev-sdk/)
2. **PUBLISHED** — Sign in to the Dashboard, open Faucet, paste the spending account's `qor1…`, press **Request Tokens**, save the faucet hash and verify the balance with the explorer on Testnet. The explorer uses the header network selection even though the faucet itself always funds Diana. [Faucet walkthrough](https://docs.qorechain.io/dashboard/faucet/) · [Explorer](https://explore.qore.network/)
3. **PUBLISHED** — For a real EVM deployment, use Node.js ≥22.13 and pnpm. Scaffold a dedicated testnet Hardhat project as below. Copy the template's `.env.example` to its ignored `.env` and set `QORE_NETWORK=testnet`. Hardhat Ignition reads `PRIVATE_KEY` for the deployer. The window helper can derive the same account and its PQC key from `QORE_MNEMONIC` (account index 0 on the Ethereum derivation path), or take the deployer's `PRIVATE_KEY` with a persistent `QORE_PQC_RECOVERY_CODE` generated by `pnpm window recovery-code`. Use the same funded account for both scripts. If its PQC key is already registered by a wallet, use the matching key derivation or open the window from the wallet that registered it. Run status first, register the ML-DSA key once and open a deployment-capable window. A target allowlist blocks creation, so use a short deployment window before opening the narrower runtime window required by relevant tracks. [Prerequisites](https://docs.qorechain.io/build-before-qday/prerequisites/) · [Kit scripts and config](https://docs.qorechain.io/developer-tools/chain-dev-sdk/) · [Pinned Hardhat config](https://github.com/qorechain/qorechain-sdk/blob/v0.14.0/templates/hardhat/hardhat.config.ts) · [Pinned environment example](https://github.com/qorechain/qorechain-sdk/blob/v0.14.0/templates/hardhat/.env.example) · [Builder FAQ](https://build.qorechain.io/faq#precompiles)

   ```bash
   npx create-qorechain-dapp@0.14.0 qore-gate --template hardhat --network testnet --package-manager pnpm
   cd qore-gate
   cp .env.example .env
   # Configure the funded throwaway deployer in the ignored .env first.
   pnpm window status
   pnpm build
   pnpm test
   pnpm window register
   pnpm window open
   # Wait about 10 seconds after window opening and then deploy.
   pnpm deploy:testnet
   ```
