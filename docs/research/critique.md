# Build Before Q-Day judge’s critique

**Recommendation: build Alajo as one trader-owned savings journey, conditional on a live withdrawal spike. Drop Oga’s Agent for this deadline. Keep a focused Quantum Pass entry in reserve.** Alajo earns its place only if the demo shows the collector receiving their agreed fee while the trader retains exclusive withdrawal authority over their own principal. Rosca already owns the broad “organizer can’t run with the savings” pitch.

Review date: 22 November 2026. I read the four project research files, opened the gallery entries linked below, and checked official docs and selected existing Diana transactions read-only. Gallery descriptions are entrant claims unless corroborated below. All three ideas are drafts. Their scores forecast feasible proof within the build window.

## 3. Technical feasibility

### B · Linked authorization works on Diana. The window is a separate control.

**Yes, an off-chain agent can spend under actual on-chain rules today.** Diana runs v3.2.8. Its live abstract-account config returned `enabled: true`, and the protocol-feature endpoint reported both abstract-account hardening and EVM target scopes enabled. In the linked-key path the owner hybrid-signs the spending rule and link, the agent proves possession of its own key, and the agent signs each authorized call with that key and its own authenticator nonce. A separate funded relayer hybrid-signs the native envelope for `MsgExecuteEVM` and pays fees. The call runs from the owner’s canonical account. The owner’s ML-DSA key can stay offline between owner actions such as link, revoke and periodic re-link. v3.2.8 requires the possession proof and a suitable enabled rule before a spend-capable link. Use the narrow `evm` permission and a selector-level rule for `pay`. [Network version](https://docs.qorechain.io/appendix/version-history/) · [Diana AA config](https://api-testnet.qore.host/qorechain/abstractaccount/v1/config) · [Diana feature flags](https://api-testnet.qore.host/qorechain/pqc/v1/protocol_features) · [Authenticators guide](https://docs.qorechain.io/sdk/guides/authenticators/) · [Account abstraction](https://docs.qorechain.io/developer-guide/account-abstraction/)

**Existing live proof.** I queried the public Diana REST API for two Invoice Leash transactions. `EEA09FD5…19EE3` contains `MsgExecuteEVM` and the 800,000 uqor payment. `DACBD4A6…505FC` contains `abstractaccount_execution_failed` with a call-allowlist rejection despite outer transaction code 0. A receipt must inspect the execution outcome and balance or payment event. An accepted failed execution can consume the authenticator nonce. Separately, I verified Leashed’s `4982A471…47CE` as a successful `MsgOpenEVMWindow` with one vault target, 17,280 blocks, 25 transactions and a 1,000,000 uqor budget. Its `FD244C8B…7212D` is a successful ordinary EVM payment from a separate run. These receipts demonstrate the two mechanisms. The linked example spends test QOR and does not establish Oga’s fUSD path. [Linked payment receipt](https://api-testnet.qore.host/cosmos/tx/v1beta1/txs/EEA09FD535D98F1FD710929D3ED1BC7343CC07F191AF6C2DEAB1FB5427A19EE3) · [Linked refusal receipt](https://api-testnet.qore.host/cosmos/tx/v1beta1/txs/DACBD4A6D4C5EF8E1C45EFC215A6FE5B387F69BA2CF0F5BEA30EAFEA703505FC) · [Scoped window receipt](https://api-testnet.qore.host/cosmos/tx/v1beta1/txs/4982A47165D1C6B10FAF240CE57CE8432EF333FD39E11762FF69F257219547CE) · [Ordinary EVM payment receipt](https://api-testnet.qore.host/cosmos/tx/v1beta1/txs/FD244C8B0ADE0C3B9BFA86BC9961EFD46C4733A4F4EB179E54D18710F427212D) · [Leashed repo](https://github.com/hackerjose25/QuoreHack)

**The combined claim needs two paths.** Relayed `MsgExecuteEVM` does not require or consume a window. An ordinary `MsgEthereumTx` uses the sender account’s hybrid-opened window, with block duration, transaction count, native QOR value plus gas and outer target restrictions. The linked key cannot open or renew that window. The prize FAQ expressly asks for the agent’s own scoped window. A qualifying design should show a real, relevant ordinary agent action under its own window and a real linked-key execution with spending rules, plus authenticated messaging. An owner-only window or an open-window screenshot leaves the agent-window criterion unresolved. The gallery’s integration badges show detected features and do not settle how jurors will treat a specific two-path design. [Builder FAQ, track gate](https://build.qorechain.io/faq#rules) · [Builder FAQ, execution paths](https://build.qorechain.io/faq#agents) · [AI Agents prize](https://build.qorechain.io/prizes#pq_ai_agents) · [Chain developer kit](https://docs.qorechain.io/developer-tools/chain-dev-sdk/)

**The payment and input still need their own controls.** A window’s native-value budget does not cap fUSD. Documented smart-account rules can meter the owner’s configured ERC-20 balance and allowance changes with token-denominated limits. If a vault holds the fUSD, its contract needs to enforce the actual token amount and allowed beneficiary. The selector scope limits what function the linked key can call, while contract logic still checks who gets paid. Treat a Telegram voice note as input. Authenticate the normalized payment intent, bind it to payee, exact amount, token, expiry and a unique nonce or order ID, and verify it before autonomous execution. Show an accepted intent and a tampered or replayed one. [Account abstraction rule semantics](https://docs.qorechain.io/developer-guide/account-abstraction/) · [Leashed’s token-limit explanation](https://github.com/hackerjose25/QuoreHack) · [QoreX message signing](https://build.qorechain.io/faq#qorex)

**SDK version.** v0.15.0 is a published source release. Its change is feature-first selection of signing formats and the authenticator digest, with `abstractaccount-hardening` selecting v2 on Diana. It did not introduce the delegated-spend path. The TypeScript npm `@qorechain/sdk` latest checked for this review was 0.14.0, which documents v3.2.8 linking and execution helpers. Invoice Leash reports using it. For TypeScript, pin a published version with those helpers and verify the digest on Diana. ### A · QCAI two-stage audit

1. **Stage 1.** Sign in to Dashboard → AI Audit, paste the Alajo Solidity source and select an **EVM/Solidity** setting, for example Ethereum (EVM/Solidity). Export the dated PDF. The QoreChain CosmWasm setting is for CosmWasm and produces a mismatch on Solidity. [Auditor guide](https://docs.qorechain.io/dashboard/contract-auditor/) · [Audit FAQ](https://build.qorechain.io/faq#audit)
2. **Disposition.** Account for every Stage 1 finding in `docs/AUDIT.md` or link a public response. Record the fix, the named regression test, or the reason a finding is a false positive or needs no contract change. Document where `pqcVerify` and any `pqcKeyStatus` calls protect funds and which tests exercise them. [Audit FAQ](https://build.qorechain.io/faq#audit)
3. **Stage 2.** After working through the findings, run QCAI again on the resulting source with the **same setting**. Keep both dated PDFs in `docs/audit/`, and point to them and the disposition from both the README and the project’s **How it’s made** field. The repo is the submission surface for the reports. Zero findings and an improved score are unnecessary. Jurors read the reports and responses together. [Audit FAQ](https://build.qorechain.io/faq#audit)
4. **Limits.** The first run each UTC day is free after sign-in. Further testnet runs cost test QOR at the displayed price, so two complete runs can use separate UTC days. The auditor reviews pasted source only and does no compile, test or runtime analysis. Solidity readiness normally shows **Not scored**. The FAQ says an EVM setting aware of QoreChain’s PQ precompiles is planned. Budget the scoped runtime window, real precompile calls on Diana, and Foundry or Hardhat tests separately. I found no published numerical Solidity input-size limit in the cited guide. [Auditor limits](https://docs.qorechain.io/dashboard/contract-auditor/#limits-and-known-issues) · [Audit FAQ](https://build.qorechain.io/faq#audit) · [Post-Quantum dApp prize](https://build.qorechain.io/prizes#quantum_safe_dapp)

**Alajo’s deciding proof.** After registration and funding, open a window scoped to the deployed vault and needed token calls. Prove that an exact trader-signed withdrawal succeeds and a collector withdrawal attempt fails even with the collector’s window open. Add a legitimate fee claim. Store the principal and fee separately, bind withdrawal signatures to the trader, chain, contract, recipient, amount, nonce and expiry, and show a replay refusal. Link the hybrid window-opening receipt and the EVM withdrawal and refusal evidence separately. `pqc_hybrid_verify status=verified` on the window-opening transaction proves the opening signature. The call outcome proves the vault’s withdrawal policy. Only label a refusal as a mined revert when the chain actually includes it. ## 4. One better fallback

**Short Delivery · Quantum Pass.** When a shopkeeper confirms how many crates actually arrived, they get a receipt their supplier can verify before settling the bill, and QoreChain gets a hybrid-signed delivery acceptance on Diana.

Show one short delivery with a clear difference between ordered and received quantities. Make the receipt bind the order ID, count and accepting wallet to a first confirmation in a small Diana receipt registry. Scaffold the app, connect QoreX, deploy the registry, and show a real hybrid transaction bound to the receipt as well as the recorded confirmation. Prove the original count verifies and a changed count fails. QoreWatch alerts on activity, QDay Proof explains the signature, QoreStamp proves a file existed and The Record finalizes a shared document version. Short Delivery has a narrower, distinct payoff: it records the buyer’s accepted quantity for one order before settlement. It is a stronger pitch than C’s unspecified bot, though the gallery snapshot establishes no guaranteed place. [QoreWatch](https://build.qorechain.io/p/qorewatch) · [QDay Proof](https://build.qorechain.io/p/qday-proof) · [QoreStamp](https://build.qorechain.io/p/qorestamp-2) · [The Record](https://build.qorechain.io/p/the-record) · [Quantum Pass](https://build.qorechain.io/prizes#quantum_pass)

**Decision rule:** Choose A if the initial test produces a live `pqcVerify` withdrawal and a role-based refusal, and the Dashboard is available for Stage 1. Keep the collector fee and individual principal as the entire demo. If the spike fails or the audit access remains blocked, switch to Short Delivery as the primary entry.
